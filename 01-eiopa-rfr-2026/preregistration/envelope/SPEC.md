## 3. The egress
- **One way out.** The builder sits on a Docker network marked internal — no route beyond it; the egress sits on that network and on an outer one. The builder's CLI reaches its vendor through `HTTPS_PROXY=http://egress:8080`; anything that ignores the proxy has no route.
- **One route, by phase.** `EGRESS_ROUTE` — `chatgpt` for builder A, `gemini-api` for builder B (§3b); `google`, the Code Assist route, kept with its controls and not run — and `EGRESS_PHASE` — `signin`, the operator's sign-in, or `run`, the builder's run. The route's hosts, on port 443, and on them its methods and paths, each matched whole without its query, each in its own phase:
  - *builder A* — `auth.openai.com`: the device code's two paths (`/api/accounts/deviceauth/usercode`, `/api/accounts/deviceauth/token`) and `/oauth/revoke` in the sign-in, `/oauth/token` in both; `chatgpt.com`: `/backend-api/codex/responses`, `/backend-api/codex/models` and `/backend-api/wham/accounts/check` in the run — not `/backend-api/wham/settings/user`, the user's settings the CLI's git-attribution extension asks for (`codex-rs/backend-client/src/client.rs:547`–`551`, `:739`; `codex-rs/ext/git-attribution/src/policy.rs:74`–`87`): refused, its error leaving that extension's policy unset, the run otherwise unchanged;
  - *`google`, the Code Assist route — not run since the vendor's change (§3b)* — `oauth2.googleapis.com`: `/token` and `/tokeninfo` in both; `www.googleapis.com`: `/oauth2/v2/userinfo` in the sign-in; `cloudcode-pa.googleapis.com`: the Code Assist setup methods (`loadCodeAssist`, `onboardUser`, `retrieveUserQuota`, `listExperiments`, `fetchAdminControls`, an operation's poll) in both, its global user setting in the sign-in, `streamGenerateContent`, `generateContent`, `countTokens` and `recordCodeAssistMetrics` in the run.
  Every other host, path or phase is refused with 403 and logged: the host, the port, the path, the time.
- **The credentials held.** The plan's real tokens never enter the builder's container. Each token a token endpoint answers — `access_token`, `refresh_token`, `id_token` — is kept by the egress in the run's `vault/`, mounted into it alone (mode 600, written whole and renamed), and the CLI is answered a stand-in: a JWT keeps its header and its claims, which the CLIs read — the expiry, the account's id —, its personal claims (`email`, `name`, `picture` and the like) masked and its signature replaced; any other token is replaced whole; the same real token is always answered the same stand-in. On each request the egress puts the real token where its stand-in stands — the `Authorization` header, a token request's body, a query's `access_token`; a request carrying a token it does not hold — the real one among them — and any API key, in a header or a query, are refused. The userinfo and token-info answers are masked the same way. The builder's credential file holds stand-ins alone: read or copied, they open nothing outside the egress.
- **HTTP only.** A WebSocket upgrade is refused with 426 and logged. Builder A's CLI opens a WebSocket to `/backend-api/codex/responses` by default and, on 426, streams over HTTP with server-sent events for the rest of its session, by its own code (§4). Every request then crosses as an HTTP request the egress reads whole; a WebSocket's frame, should one ever pass, is refused and its connection closed.
- **Each request read.** The egress ends TLS under a certificate authority made for this run alone (`run.sh`; its private key never enters the builder), which the builder's CLI trusts through `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS` and `CODEX_CA_CERTIFICATE`. Each request's decoded body and path give its line in `egress.jsonl`: its model, its reasoning or thinking setting, the names of the tools it declares and every tool of another kind, wherever its route declares them — builder A's body: `model`, `reasoning`, `tools` and every `additional_tools` input item, a namespace's tools read at any depth, each named under its namespace's name — `functions.exec` — (`codex-rs/tools/src/responses_api.rs:54`–`63`, `:76`–`81`); builder B's: `model` at its top, `request.model` for a count of tokens, `request.tools` and `request.generationConfig.thinkingConfig`. A generation request whose body the egress cannot read, naming no model, or carrying a namespace whose tools it cannot read — no list of tools, or nested deeper than four — is refused. The body of each request to the model and of each setup, account or metrics request is kept, gzip-compressed, under `egress/bodies/`; its sha256 is on the line; a token request's body is never kept. No header, token or stand-in is written; a token or a key in a query string is written as `REDACTED`.
- **One model.** `EGRESS_MODELS` — `gpt-6-astra` for builder A, `gemini-4-argon` for builder B, the test's model in builder B's test of its route alone (§7): a generation request naming any other model is refused with 403 and logged. Each CLI's configuration sends every request it makes to its configured model (§4); a refusal of this kind is a finding, and the dry run must show none.
- **Refused at the wire:** a request that declares, at any depth of a namespace, a tool its vendor runs to reach beyond its servers — any `web_search` kind, `mcp`, `code_interpreter`, `computer_use_preview`, `computer`, `image_generation`, `file_search` (OpenAI); `googleSearch`, `googleSearchRetrieval`, `urlContext`, `codeExecution`, `googleMaps`, `enterpriseWebSearch`, `computerUse`, `retrieval`, `fileSearch` (Google). The CLI's own configuration already leaves them out (§4); the egress makes the claim hold whatever starts the request — the CLI, or a command the agent runs in its shell. A refused request reached nothing; it is logged with its reason and named in the run's record.
- **Streams pass as they come — a generation's alone.** A response of type `text/event-stream` to a generation request is passed through unbuffered, its bytes unchanged — and so is builder A's answer to a generation asked with `stream` true and answered 200, whatever its type: the ChatGPT route's answers carry no `content-type` (dry-a1, dry-a2), and its CLI reads their bytes as server-sent events all the same (`codex-rs/codex-api/src/sse/responses.rs:38`–`97`, `:541`–`548`); its status and its type are logged, with builder A's `openai-model` or `x-openai-model` header where its answer carries one. A stream on any other request is replaced by 502. Builder A's stream — asked unencoded — is read on the side as it passes, where its CLI reads the model that served (`codex-rs/codex-api/src/sse/responses.rs:190`–`209`, `:244`–`262`, `:269`–`278`): at its end or its cut a `served` line names the model each `response.created`, `response.completed` or `response.incomplete` event names, any `openai-model` or `x-openai-model` in an event's `response.headers` or `headers`, the `safety_buffering` value as its CLI picks it — an event's own field when present, whatever it holds, else a `response.metadata` event's metadata of that type (`codex-rs/codex-api/src/sse/responses.rs:174`–`183`, `:248`–`258`) — by its kind alone: absent, `false`, an object or that metadata with its `retry_model` or without — what the CLI reads as a safety-buffering event, its faster model the answers' header's where it names none (`:259`–`265`; `codex-rs/codex-api/src/common.rs:135`–`142`) —, any other value by its type; and the number of events — a stream it could not read, or an answer in which it read no server-sent event, named; nothing else of it is kept. Builder A's route names the model that served in each stream's `response.created` and `response.completed` — `gpt-6-astra` on all 36 of its third dry run's —, and no answer carries `openai-model`. Builder B's stream is read on the side the same way — its server-sent events, for the use its last one carries (§3b).
- **The plans' limits recorded.** Each response's line carries builder A's `x-codex-*` headers — its plan's windows, their use, their resets —, an observation read for no criterion, the weekly window the operator's to watch; `x-codex-turn-state`, an opaque routing value the CLI replays within a turn (`codex-rs/core/src/client.rs:291`–`311`), is not logged; on the Code Assist route its setup answers — its tier, its quota by model, its experiments — are kept under `egress/bodies/`; builder B's spend is counted at the egress and held to its cap (§3b). A run a plan's limit ends returns what exists, named as ended by the plan.
- **Fail closed.** An error inside any of its hooks refuses the request (403) or replaces the response (502); a token answer it cannot read, 502. At load the addon writes `egress/addon-ready-<phase>.json` — the route, the phase, the models, its own sha256, the number of real tokens the vault holds, builder B's spend cap and the rates it prices by —, which the egress's health check requires: an addon `mitmproxy` could not load leaves the builder unstarted.
- **The image:** the `mitmproxy` project's own, at the release and digest pinned at the build (§9).

## 3b. Builder B's route — the Gemini API, its key held at the egress
Since 18 June 2026 the Gemini CLI serves no individual or Google AI plan, only a paid Gemini API key or a Code Assist licence. Builder B runs on the Gemini API with one key of a project of the lab's own, its billing on prepaid credits: at a zero balance the key stops — the run's hard limit.
- **The key held.** The operator types the key at `run.sh`'s prompt, not echoed. `run.sh` writes it, with a stand-in it makes — `rt01.api_key.` and 48 random hexadecimal digits —, into the run's `vault/vault.json` (mode 600), mounted into the egress alone, and gives the builder the stand-in alone, as `GEMINI_API_KEY`, through `builder.env`. The key is never an argument, a variable of the operator's environment or a file outside `vault/`; it never enters the builder's container.
- **The route.** `EGRESS_ROUTE=gemini-api`, in the run phase alone — there is no sign-in: `generativelanguage.googleapis.com`, port 443; `POST /v1beta/models/<model>:streamGenerateContent`, `:generateContent` and `:countTokens` (`v1` and `v1alpha` as well), and `GET` of the model list or of a model's entry; every other host, path or method is refused (403) and logged. A generation request's model is read from its path, and from its body when the body names one; its thinking level from `generationConfig.thinkingConfig`; its tools from `tools`. Another model, a server-side tool — `googleSearch`, `urlContext`, `codeExecution` and the like —, a WebSocket upgrade: refused, as on every route.
- **The key on the wire.** On each request the egress puts the real key where its stand-in stands — the `x-goog-api-key` header, which the CLI sends (§4.2), a query's `key`, or a bearer token; a request carrying another key — the real one among them —, another key header, or no key, is refused, and a refused request never carries the key. The key and its stand-in are never logged; a query's key is shown redacted. The egress does not start without exactly one key in its vault: no ready marker, no builder.
- **The checks.** Before the run, `run.sh` checks by `vault_check.py key B`, in the run's own image, offline: one key in the vault; `builder.env` giving the builder its stand-in, not the key; no real key under `state/`, `logs/` or `work/`. After the archive, the scan of §6 reads every member for the real key. `vault/` is removed whenever `run.sh` exits.
- **The spend — counted at the egress, held to a cap.** Each answered generation — the main loop's, a compression's or a loop check's, a retried one's — carries its use in its answer, `usageMetadata`: a stream's last event, a JSON answer's own. The egress asks the API for answers without a content encoding — `accept-encoding: identity` on each generation — and reads a gzip or deflate one all the same; it reads each answer's use as the answer passes, prices it at its rates for the date the answer ends — `gemini-4-argon`, per 1M tokens: input $2.00, input from the API's cache $0.10, output with the model's thinking $10.00 to 30 November 2026; $4.00, $0.20 and $20.00 from 1 December, by the vendor's pricing page as read on 29 October 2026 —, and writes a `use` line beside the request's: the tokens, the price, the run's sum, the cap. Once the sum reaches the cap — `EGRESS_SPEND_CAP_USD`, $55 a run, set by `run.sh` —, every further generation is refused with 402, «the spend cap», and logged; a count of tokens passes. The CLI does not retry a 402 (`packages/core/src/utils/retry.ts:192`–`199`): its run ends — «stopped by the spend cap» (§6) —, not restarted (the preregistration's §8). The overrun is the answer in flight when the sum reaches the cap — one, as the CLI sends one request at a time (INFERRED). Every generation the egress lets through is counted as the vendor may bill it, its answer read whole or not: one cut — by the CLI or the server — after its answer's headers, or before any answer, is counted at a bound, its `use` line marked so with its cause: its thinking and output at 32,768 tokens at the output rate — or what its events showed, where more —; its input by the last use any of its events carried, else uncached by its request body's bytes at the run's last ratio of a body's bytes to its prompt's tokens — one byte a token before any answer has set the ratio —, that send re-priced on a line of its own by its resend's own use when the CLI sends the same body again. The vendor's billing page says a request failing with 400 or 500 is not charged, and nothing of an answer the client cut: the bound holds the cap to what may be billed. Each stream's events, and those carrying a use, are counted on its line. An answer that ends whole without a use the egress can read, or a generation it cannot price, stops the count: every later generation refused, 402, «the spend unmeasured». Without its cap, or without rates for its model, the egress does not start on this route. Beside the egress's sum: the CLI's own record — its last `stream-json` event, or the session file's model turns when the limit stopped it — and the meter of the run's project in its vendor's console, that project's alone, read within 24 hours of the run, its tax named — the cap counts the vendor's prices before tax, and the meter of an individual's billing account adds the VAT its country requires; the effort log carries the three. A run ended by the vendor's unavailability counts its own use like any run. The backstop: the project's prepaid balance, on a billing account of its own — at $0 its key stops, after up to about ten minutes of overage.

## 6. The archive
When the builder stops — its CLI ended, or stopped by the time limit — `run.sh` stops the egress and packs the run's `work/return`, `logs`, `state` and `egress` folders into `run-<id>.tar.gz`, then prints the archive's sha256 as the console's last line, which it also writes to `run-<id>.sha256`. When the limit stopped the CLI, the return is the copy made at the deadline: `run.sh` packs it as `work/return` — its files checked by `logs/return-at-deadline.sha256`, whose sha256 the console carries from the deadline — and the CLI's folder as it ended beside it as `work/return-after-deadline`, a later write, not the return. No one opens the run's folders before that line; the archive's sha256 is checked before the archive is opened. Each run is read in one order: the archive's sha256 first; then the launch print and the egress log, checked against the preregistration's §4 and this spec item by item, the check recorded; then the return. A run of builder B is read as well for its CLI's five rules (§4.2), by command from its events, its session file and its egress log — the shell calls its policy denied, the calls of a cut stream run beside its resend's, the tool outputs cut at 64 KiB, the streams cut at 300 seconds, the history's largest prompt —, each counted and named in the run's record, none voiding it. A run of builder B is read for its end before its return, by `run_end.py` over the archive's `egress/egress.jsonl`, `logs/cli-stderr.txt`, `logs/cli-events.jsonl` and `logs/exit.txt`: «stopped by the spend cap» when the egress refused a generation for the run's cap or for a use it could not read (§3b), whatever the exit status; «stopped by the time limit» when `exit.txt` names status 124; «ended by the plan's limit» when the CLI ended on an error and an attempt of its last model request was answered 402, or 429 naming the plan's limit — the balance, its credits, billing, a spending cap or a quota, by the words the egress finds in the answer's error and logs without its message; «ended by the vendor's unavailability» when the CLI ended on an error after its retries on one model request — its error output naming those attempts, «Max attempts reached» on the last or the last one cut — and each of that request's attempts in the egress log ended without a 2xx — answered with 429, 499 or a 5xx, or cut by the CLI at its headers timeout — 60 seconds as shipped, 600 by the experiments file (§4.2) — with no response —, none refused by the egress from the first attempt on, no 400, 402 or 404 among the answers and none naming the plan's limit; any other end «ended by the builder». A run stopped by the spend cap or ended by the plan's limit is not restarted. A run ended by the vendor's unavailability is restarted as the preregistration's §8 says, up to twice, each restart a run of its own under a new id — `run.sh` refuses an id whose folder, archive, console or sha256 exists —, the ended run's archive and findings kept beside the restart's. Not packed: `in` — the brief, the PDF and the bundle, each named with its sha256 in the launch print —, `ca` and `vault`. Builder A's archive carries three symbolic links its CLI makes under `state/codex/tmp/arg0-linux/`, absolute, into the image's `/opt/clis/`: a reader's extraction refuses or skips them — Python's `tarfile` with its `data` filter refuses them —; they hold nothing of the run. Once the archive is made, `run.sh` scans it, by `vault_check.py` in the run's own image, offline — every member read whole, a gzip member opened — for each real token the vault holds — builder B's key among them —, as it is, URL-escaped or JSON-escaped, and prints the count of hits beside the egress's own counts of tokens issued and swapped: a hit is a finding, and `run.sh` exits non-zero. Then it removes `vault/` — removed in any case when `run.sh` exits — and prints the archive's line last.
The archive carries the text and the inputs: the CLIs' session files under `state/` and the request bodies under `egress/bodies/` hold what the builder read — pages of the PDF, the bundle's values. The archive stays out of this repository, which receives the builds as returned, each `egress.jsonl` and the archives' hashes, each through the leak check (the preregistration, §10).

## 7. The dry run
`run.sh <A|B> dry-<n> --dry` — after builder A's sign-in, after builder B's key (§5) — mounts `dry-run/brief.md` as the brief and a padding file in place of the text and the bundle; the time limit is 15 minutes; builder B's settings are the real run's, key for key — `model.compressionThreshold` 1.0 —, and so is its spend cap. The brief's step 9 is one command that prints a line each minute for 30 minutes: one model turn's calls run together (`packages/core/src/scheduler/scheduler.ts:492`, `:532`), and one call outlasts the limit whatever the model batches, its output keeping the shell's 300-second inactivity timeout from firing (`packages/core/src/config/config.ts:1315`; `packages/core/src/tools/shell.ts:668`). Its step 8 reads the padding in two calls of 2,000 lines — a `read_file` given its first and last line returns the range whole (`packages/core/src/utils/fileUtils.ts:648`–`657`) —, each reaching the model cut at 64 KiB (§4.2, rule 3) — the prompt raised to about 59,500 tokens in the second dry run, past the 20,972 at which the first, its threshold lowered to 0.02, compressed; at 1.0 none followed (§4.2). Builder B's three dry runs were stopped by the limit before step 9's command ran — in the second and third the vendor held the stream that carried it (§4.2, rule 5) —: a command running at the deadline is builder A's dry run's to show. Builder A's fourth dry run met every criterion, the fourth in its form: a write to the mounted inputs by its CLI's file tool failed without naming its cause — the read-only mount its evidence —; no event carried a `safety_buffering` value but absent or `false`, no buffering event ran, and a request for the faster model an answer's headers can name would be refused at the wire. Its criteria, fixed before it runs: `dry-run/criteria.md`. Its archives' sha256 and its findings are recorded before the freeze, and named in the preregistration (§4).
`run.sh B test-<n> --test <model>` — builder B's test of its route on the Gemini API (§3b), before its dry run: the dry run's inputs, time limit and criteria, its settings made at launch from `dry-run/gemini-settings.json` by one command — every `"gemini-4-argon"` replaced by the test's model, the count of replacements and both files' sha256 on the console —, `EGRESS_MODELS` that model alone. It tries the envelope — the key held, its stand-in, the route's hosts and paths —, not builder B's model: it is not the dry run. Its archive's sha256 and its findings are recorded beside the dry run's and named at the freeze. The egress prices a test's answers by its model's rates: a model without rates in its table — `gemini-3.1-pro-preview` among them — does not start on this route until a revision adds them.

## 8. What it does not show
- How a builder reads the text: the dry run mounts none; in the runs, the CLI's record of its tool calls is the CLI's own account.
- That a model was not trained on the text: an egress log shows only what passed the envelope.
- What the vendor does on its own servers with a request the egress let through.
- That no request but the CLI's uses the plan or the key: the real tokens and the key never enter the container, but the stand-ins — builder A's in its credential file, builder B's in the CLI's environment —, which the agent's commands can read, open the route through the egress for them as for the CLI. The egress's rules hold whatever sends a request: another host, path or phase, another model or a tool its vendor runs beyond its servers is refused, and every request is logged.
- The plan's session at the vendor after the run: the vault's removal leaves no real token on the operator's disk; the session stays until it expires or the operator signs it out at the vendor. Builder B's key stays valid at its vendor until the operator deletes it or its credits run out.
- The cap's end in a run: the dry run does not reach builder B's cap; the 402 and the count behind it are shown by the egress's controls, the CLI's answer to a 402 read at its tag. The egress's sum and the vendor's meter can differ: a generation cut before its use was read is counted at its bound, which the vendor may bill below; the meter keeps its own rounding, the day's exchange rate and its tax. The experiments file's effect, in a run whose answers all begin within 60 s: shown by its check on the pinned CLI (§4.2), not by the run.
- Builder A's CLI read for rules of the kind §4.2 names for builder B's: not read; a run that meets one names it in its record.
- A run's long tail: whether a five-hour history reaches either CLI's compression — builder A's at 784,800 tokens (§4.1), builder B's at the model's whole limit (§4.2) —; which model the vendor served each generation — the egress log's lines its record, builder A's `served` lines among them (§3) —; whether builder A's model sets a goal whose continuation runs before `exec`'s end (§4.1). The dry runs met none of these; a run that meets one names it in its record.
- Anything about the operator's machine beyond the container: the envelope trusts its Docker runtime.
